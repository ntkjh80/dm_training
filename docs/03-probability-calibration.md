# 03. 확률과 확률 보정

다음 숫자는 개념을 설명하기 위한 가상 예시입니다. 담당 팀 확률이 billing 0.82, technical 0.10, sales 0.05, other 0.03이라면 billing이 가장 유력합니다. 그러나 이 고객 건이 반드시 82퍼센트의 객관적 진실을 가진다는 뜻은 아닙니다.

## 보정은 확신의 크기를 조절한다

비슷한 조건에서 0.8 정도의 확률을 낸 판단 100건을 모았을 때 약 80건을 맞히면 그 구간의 확률이 잘 보정되어 있다고 말합니다. 실제로는 55건만 맞히면 모델이 지나치게 자신만만할 수 있습니다. 확률 보정은 점수와 실제 빈도의 관계를 조정합니다. 정답이 잘못 붙었거나 입력 분야가 바뀌면 보정도 다시 확인해야 합니다.

학습에 쓰지 않은 별도 데이터로 보정하고, 최종 시험 데이터에서 정확도와 보정 상태를 함께 확인합니다. 보정에 사용한 자료의 수치만으로 성능을 보고하면 낙관적으로 보일 수 있습니다.

근거: [12. 확률 보정의 의미](https://scikit-learn.org/stable/modules/calibration.html)

## 정확도와 보정 오차는 서로 다르다

| 지표 | 쉬운 질문 | 주의할 점 |
| --- | --- | --- |
| Accuracy | 전체 질문 중 몇 개를 맞혔는가 | 자주 나오는 답만 골라도 높을 수 있음 |
| Recall | 실제 환불 요청을 얼마나 찾아냈는가 | 누락 비용이 큰 업무에서 중요 |
| Precision | 환불로 골랐던 것 중 진짜 환불은 얼마인가 | 불필요한 검토나 잘못된 배정 확인 |
| ECE | 확률 구간별 확신과 적중률이 얼마나 다른가 | 표본 수와 구간 나누기에 따라 변함 |
| 처리 시간 | 응답까지 얼마나 기다렸는가 | 최초 로딩과 이후 추론을 나누어 기록 |

## confidence와 확률을 혼동하지 않는다

API의 confidence가 선택지 확률과 같은 숫자라는 보장은 없습니다. 예제에서는 probabilities 안에 있는 해당 팀의 값을 사용합니다. noul은 예의 확률입니다. 낮으면 아니오를 뜻할 수 있으므로 낮은 숫자를 항상 불확실함으로 읽어서는 안 됩니다.

score에서 단계 확률이 [0.1, 0.6, 0.3]이면 가장 유력한 단계는 1이고, 확률로 평균한 점수는 1.2입니다. Python의 answer와 API의 score는 서로 다른 표현일 수 있습니다. 업무에 어느 값이 필요한지 먼저 정합니다.

근거: [2. 로컬 Decision API와 Laya](https://unsloth.ai/docs/models/decision-laya) · [11. 정답과 확률 처리 구현](https://github.com/unslothai/unsloth/blob/main/unsloth/models/_decision_common.py)

교육용 처리 예: 최고 선택지 확률이 0.8 이상이면 담당 팀 후보를 표시하고, 그보다 낮으면 사람 검토로 보냅니다. 0.8은 설명용 시작값입니다. 실제 기준은 별도 검증 자료에서 자동 처리 비율과 오류를 함께 보며 정합니다.

## RAG에서 확률을 읽는 예

문서 C1의 유용성 0.94와 C3의 유용성 0.87은 서로 다른 `noul` 질문의 값입니다. 두 문서가 모두 유용할 수 있으므로 합이 1일 필요가 없습니다. 이것을 하나의 `choice` 분포처럼 정규화하면 의미가 바뀝니다.

각 문서의 관련성 확률과 문서 묶음 전체의 답변 가능성 확률도 서로 다른 질문의 결과입니다. 하나를 다른 하나로 대체하거나 단순히 평균해 충분성을 보장할 수 없습니다. [두 단계 판단 그림과 사례](15-rag-decision-gates.md)에서 비교합니다.
